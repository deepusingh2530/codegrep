# Rule authoring

Every rule is one small YAML document plus two fixtures. This page covers the
engine contract a pattern must respect, the schema, the validation loop, and
how to get a rule merged. Severity discipline and what is deliberately *not*
flagged are in [`coverage-policy.md`](coverage-policy.md); the pipeline is in
[`architecture.md`](architecture.md).

The normal workflow is: write a JSON spec, generate YAML + fixtures, run the
fixture gate.

```sh
$EDITOR scripts/specs/my-rule.json
python3 scripts/mkrules.py scripts/specs/my-rule.json
./target/release/scanward rule test rules/
```

## Engine contract

Patterns are code-shaped with three wildcards, compiled to a regex over whole
file text, whitespace-insensitive and multi-line.

| Token | Meaning |
| --- | --- |
| `$VAR` | one code unit. Lazy (`.+?`) mid-pattern, greedy (`.+`) only when trailing |
| `$...ARGS` | variadic filler; prefer `...` for plain argument lists |
| `...` | any text filler |
| everything else | literal — the matcher regex-escapes it |

Consequences worth knowing before you write a pattern:

- **No character classes, no alternation, no anchors** in the pattern itself.
  Put that logic in `metavariable-regex`.
- **Keep the dangerous API literal in the pattern.** It feeds the Aho-Corasick
  pre-filter; a pattern with no extractable literal disables the fast path for
  every file.
- **One call or statement shape per pattern.** Two shapes means two rules (or
  `pattern-either`).
- A pattern with `, ...` (e.g. `f($VAR, ...)`) **misses single-arg calls**. Emit
  both `f($VAR)` and `f($VAR, ...)` via `pattern-either`.
- Patterns are matched over the whole file with DOTALL, so a trailing `$VAR`
  captures to end of file — do not rely on that to scope a match.
- `metavariable-regex: {VAR: <regex>}` constrains one capture with an
  **unanchored** search. Use it for shapes like "the argument is user input",
  not for exact equality.
- A metavariable that does not match anything is **skipped**, not failed — a
  pattern with no capture therefore ignores its constraints.

## Schema

One rule per YAML document; several rules may share a file as a YAML sequence.
`mkrules.py` writes this shape from a JSON spec (`scripts/specs/`).

```yaml
id: py-subprocess-shell          # unique, kebab-case; becomes a fixture directory
languages: [python]              # a recognized language, or generic
severity: ERROR                  # ERROR | WARNING | INFO
category: security:code-execution
message: One line, no unescaped ": " (quote it)
fix: What to do instead
pattern: os.system($CMD)         # or: pattern-either: [{pattern: ...}, ...]
pattern-not: ...                 # optional, enforced per line
metavariable-regex:
  CMD: "[Uu]ser|[Ii]nput"       # optional narrowing
metadata:
  owasp: "A03:2021-Injection"
  cwe: "CWE-78"
  confidence: HIGH
```

Taint rules replace the pattern with a `taint:` block (`sources`, `sinks`,
`sanitizers`), each a list of `{patterns: [...]}` groups. Use taint when the
claim genuinely is "untrusted input must reach this sink"; use a pattern with
`metavariable-regex` when the sink itself is the signal.

## Fixtures

`rules/tests/<id>/fail.<ext>` must produce at least one finding from that rule
alone; `pass.<ext>` must produce none. They are per-rule: `scanward rule test`
runs each rule against only its own fixtures, so a fixture that trips a
*different* rule is fine.

```sh
./target/release/scanward rule test rules/            # all rules
./target/release/scanward rule test rules/ | grep my-id   # just yours
```

A pass fixture is where precision is proven. Write the counterexample you
actually expect in real code — the benign call a reviewer will type.

## Validation loop

1. `scanward rule test rules/<your-rule>.yaml` — schema loads, id is unique.
2. Fail fixture triggers; pass fixture stays clean.
3. On failure, adjust once and re-run; if it still misses, the pattern is
   probably over-constrained — usually a `metavariable-regex` that is too
   strict, or a single-shape pattern that needs a `pattern-either` sibling.
4. Confirm nothing else moved: run the full `rule test`, the `testdata` scan,
   and the self-scan of `crates/`. A `testdata` count that *rises* is usually a
   true positive from the new rule (the demo corpus is deliberately vulnerable);
   any other movement is a regression to investigate before merging.

## Coverage checklist

Track ideas per language × OWASP — **titles only, never content**: sqli, cmdi,
xss, ssrf, path traversal, open redirect, deserialization, ssti, xxE,
weak crypto, secrets, auth/disclosure misconfig, framework-specific sinks.

A box means "we wrote and tested an original rule for this class". It never
means "ported from a registry" — see the originality rule in
[`licensing.md`](licensing.md). The live gap list is generated by the CVE watch
into [`cve-coverage.md`](cve-coverage.md); closing a gap is the normal source of
new rule batches.

## Optional local assist

`scripts/rule-gen.py` drafts candidate rules against a local Ollama model,
validates each candidate with the same fixture gate, and writes only what
passes. It is a helper, not a reviewer: generated output is still subject to
every rule on this page, and the originality requirement applies to it as much
as to anything else.
